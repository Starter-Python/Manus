# A1-1 프롬프트 관리자 | 최적화 포인트와 확장 아이디어

현재 프로그램은 학습 목적의 **메모리 기반 콘솔 프로그램**으로, 프롬프트를 리스트와 딕셔너리에 저장하고 메뉴 선택에 따라 목록·검색·즐겨찾기를 처리합니다. 기본 예시 데이터처럼 항목 수가 적은 상황에서는 구현이 단순하고 이해하기 쉬운 현재 구조가 가장 적절합니다. 따라서 지금 단계에서 “더 빠르게” 만들기보다, 데이터가 늘어났을 때 어떤 문제가 생기는지 알고 **필요해지는 순간에만** 개선하는 것이 좋습니다.

> 결론부터 말하면, 현재 규모에서는 성능보다 **데이터 저장, 수정·삭제, 테스트 확장, 사용자 경험 개선**의 우선순위가 더 높습니다. 수백~수천 건 이상의 데이터를 실제로 다루게 될 때 검색·분류 인덱스와 SQLite 같은 저장소를 고려하면 됩니다.

## 1. 현재 코드 구조와 성능 특성

현재 `prompt_manager.py`는 `list[dict]` 구조를 사용합니다. 프롬프트를 한 건 추가하는 `append()`는 일반적으로 매우 빠르고, 목록·카테고리·검색·즐겨찾기 기능은 모든 항목을 한 번씩 확인하는 방식입니다.

| 기능 | 현재 방식 | 데이터가 n개일 때의 처리량 | 현재 과제 규모에서의 판단 |
| --- | --- | --- | --- |
| 프롬프트 추가 | 리스트 끝에 `append()` | 대체로 O(1) | 충분히 적합 |
| 전체 목록 | 모든 항목을 순서대로 출력 | O(n) | 충분히 적합 |
| 카테고리별 조회 | 리스트 컴프리헨션으로 필터링 | O(n) | 충분히 적합 |
| 키워드 검색 | 제목·내용을 모두 순회 | O(n) | 충분히 적합 |
| 즐겨찾기 목록 | `favorite`가 참인 항목 필터링 | O(n) | 충분히 적합 |
| 카테고리 목록 | 사용자 정의 카테고리를 집합으로 생성 | O(n) | 충분히 적합 |

이 프로그램은 콘솔에 결과를 출력하는 시간도 포함되므로, 수십 건 수준에서는 알고리즘보다 화면 출력 시간이 더 크게 느껴질 수 있습니다. 지금은 복잡한 캐시나 인덱스를 추가하면 코드가 어려워지고, 오히려 즐겨찾기 전환·추가·삭제 시 인덱스 동기화 오류가 생길 수 있습니다.

## 2. 우선순위가 높은 개선 포인트

### 2-1. JSON 저장·불러오기

현재 데이터는 프로그램을 종료하면 초기화됩니다. 가장 먼저 추가할 만한 기능은 `prompts.json` 파일에 데이터를 저장하고, 시작할 때 불러오는 기능입니다. 이는 성능 향상보다 **사용성·데이터 보존성** 측면에서 중요한 개선입니다.

| 단계 | 구현 방향 | 주의할 점 |
| --- | --- | --- |
| 시작 시 | 파일이 있으면 `json.load()`로 프롬프트 목록을 읽음 | 파일이 없거나 JSON이 깨진 경우 기본 데이터로 안전하게 시작 |
| 변경 직후 | 추가·수정·삭제·즐겨찾기 전환 후 `json.dump()` 실행 | UTF-8과 `ensure_ascii=False` 사용 |
| 종료 시 | 종료 직전에 한 번 더 저장 | 중간 오류로 데이터가 사라지지 않도록 예외 처리 |
| 안정성 강화 | 임시 파일에 저장한 뒤 교체 | 저장 중 프로그램이 종료돼도 원본 파일 보호 |

JSON 파일에는 비밀번호, API 키, 개인 정보가 포함되지 않도록 해야 합니다. 프롬프트에 민감한 업무 내용이 있을 수 있다면 `.gitignore`에 `prompts.json`을 추가해 GitHub에 실수로 올리지 않는 것도 중요합니다.

### 2-2. 프롬프트 고유 ID와 수정·삭제

현재는 목록 번호를 선택해 상세 보기와 즐겨찾기를 처리합니다. 목록 번호는 검색 결과나 필터 결과에 따라 바뀔 수 있으므로, 데이터가 커지고 수정·삭제 기능을 넣을 때는 각 프롬프트에 변하지 않는 `id`를 추가하는 편이 안전합니다.

```python
{
    "id": "a1b2c3d4",
    "title": "회의록 요약",
    "content": "다음 회의록을 세 문장으로 요약하세요.",
    "category": "자동화",
    "favorite": False,
}
```

`uuid` 표준 라이브러리로 ID를 생성하면 별도 패키지 없이 구현할 수 있습니다. ID가 생기면 제목이 같은 프롬프트도 구분할 수 있고, 수정·삭제·사용 기록·공유 링크 같은 이후 기능의 기반이 됩니다.

### 2-3. 입력과 화면 출력의 분리

현재 함수들은 `input()`과 `print()`를 직접 사용하므로 콘솔 학습에는 이해하기 좋습니다. 다만 기능이 늘어나면 데이터 처리 함수와 화면 입출력을 분리하면 테스트가 쉬워집니다.

| 현재 예시 | 개선 방향 | 효과 |
| --- | --- | --- |
| `find_prompts()` | 이미 입력 없이 데이터만 받아 결과를 반환 | 단위 테스트가 쉬움 |
| `add_prompt()` | `create_prompt(title, content, category)`와 콘솔 입력 함수를 분리 | 웹·GUI로 확장하기 쉬움 |
| `toggle_favorite()` | `set_favorite(prompt_id, value)` 같은 데이터 함수 추가 | 입력 오류와 데이터 처리 로직을 따로 검증 가능 |
| `show_prompt_list()` | `format_prompt_summary()`로 한 줄 문자열 생성 분리 | 출력 형식 테스트와 재사용이 쉬움 |

이 구조는 성능 자체보다 **유지보수성과 테스트 가능성**을 크게 높입니다. 앞으로 웹 화면이나 모바일 앱으로 바꿔도 데이터 처리 함수를 재사용할 수 있습니다.

## 3. 데이터가 많아질 때의 성능 최적화

아래 항목은 수십 건이 아닌 수백~수천 건의 프롬프트를 실제로 관리할 때 검토합니다. 측정 없이 먼저 적용하면 복잡도만 증가할 수 있습니다.

### 3-1. 카테고리와 즐겨찾기 인덱스

현재는 카테고리별 조회와 즐겨찾기 목록을 열 때마다 전체 리스트를 순회합니다. 데이터가 매우 많고 해당 기능을 자주 사용한다면 보조 인덱스를 둘 수 있습니다.

```python
prompts_by_category = {
    "텍스트 생성": ["id-1", "id-4"],
    "자동화": ["id-2"],
}
favorite_ids = {"id-1", "id-3"}
```

| 장점 | 비용 | 적용 시점 |
| --- | --- | --- |
| 카테고리·즐겨찾기 목록을 빠르게 찾을 수 있음 | 추가·수정·삭제·카테고리 변경 때 인덱스도 함께 갱신해야 함 | 데이터가 많고 조회 빈도가 높을 때 |
| 중복되지 않는 즐겨찾기 ID를 집합으로 관리 가능 | 원본 데이터와 인덱스 불일치 위험이 있음 | 충분한 테스트가 준비된 뒤 |

### 3-2. 검색 정규화와 전문 검색

현재 `find_prompts()`는 검색할 때마다 제목과 내용을 `casefold()`하여 대소문자를 무시합니다. 데이터가 커지고 검색이 잦아지면 저장 시점에 `search_text` 같은 정규화 필드를 미리 만들거나, SQLite의 FTS(전문 검색) 기능을 고려할 수 있습니다.

| 단계 | 방법 | 장점 |
| --- | --- | --- |
| 소규모 | 현재의 리스트 순회 검색 유지 | 가장 단순하고 충분히 빠름 |
| 중규모 | 제목·내용의 정규화 문자열을 저장 | 반복적인 대소문자 변환 감소 |
| 대규모 | SQLite와 FTS 검색 사용 | 검색, 정렬, 필터, 영속성을 함께 개선 |
| 검색 품질 강화 | 부분 일치, 태그, 오타 허용 검색 도입 | 사용자가 원하는 프롬프트를 더 쉽게 찾음 |

한국어 검색은 형태소 분석이나 초성 검색처럼 더 복잡한 요구가 생길 수 있습니다. 이 기능은 실제 사용자가 어떤 검색어를 쓰는지 확인한 뒤 도입하는 편이 좋습니다.

### 3-3. 목록 페이징과 정렬

프롬프트가 수백 건이면 한 번에 모두 출력하는 방식은 읽기 어렵습니다. 성능뿐 아니라 사용성을 위해 페이지 단위 출력이 효과적입니다.

```text
[ 전체 프롬프트 목록 | 2 / 8 페이지 ]
11. 회의록 요약
12. 주간 보고서 초안
n. 다음 페이지 / p. 이전 페이지 / q. 메뉴로 돌아가기
```

추가로 최신 등록순, 제목순, 카테고리순, 즐겨찾기 우선, 사용 횟수순 정렬을 제공할 수 있습니다. 정렬은 보통 O(n log n)이므로, 화면을 열 때마다 정렬하기보다 사용자가 정렬 기준을 바꿀 때만 수행하면 됩니다.

## 4. 기능 확장 아이디어 로드맵

### 4-1. 다음 단계: 기본 CRUD와 내보내기

| 우선순위 | 기능 | 사용자 가치 | 구현 난이도 |
| --- | --- | --- | --- |
| 1 | 프롬프트 수정 | 잘못 입력한 제목·내용·카테고리 보정 | 낮음 |
| 2 | 프롬프트 삭제와 삭제 확인 | 불필요한 항목 정리 | 낮음 |
| 3 | JSON 저장·불러오기 | 프로그램을 껐다 켜도 데이터 유지 | 중간 |
| 4 | Markdown 내보내기 | 카테고리별 프롬프트를 문서로 활용 | 중간 |
| 5 | 중복 제목 경고 | 같은 프롬프트를 실수로 여러 번 추가하는 문제 감소 | 낮음 |
| 6 | 태그 여러 개 | 카테고리 하나만으로 부족한 분류 보완 | 중간 |

CRUD는 Create(추가), Read(조회), Update(수정), Delete(삭제)의 약자입니다. 현재 프로그램은 Create와 Read를 중심으로 구현되어 있으므로, 수정·삭제를 더하면 프롬프트 관리 도구의 기본 형태를 갖추게 됩니다.

### 4-2. 그다음 단계: 기록과 개인화

| 기능 | 구현 예시 | 활용 방식 |
| --- | --- | --- |
| 사용 횟수 | 상세 보기 또는 복사 시 `use_count += 1` | 자주 쓰는 프롬프트 Top 목록 |
| 마지막 사용일 | `last_used_at` 저장 | 오래 사용하지 않은 프롬프트 정리 |
| 메모와 출처 | `note`, `source` 필드 추가 | 언제·왜 만든 프롬프트인지 회상 |
| 버전 이력 | 수정 전 내용을 history에 저장 | 좋은 문구를 실수로 덮어쓴 경우 복원 |
| 고정(Pin) | 별도 `pinned` 값 | 매일 쓰는 프롬프트를 목록 상단에 배치 |
| 변수 템플릿 | `{{주제}}`, `{{대상}}` 입력칸 | 반복 작업에서 프롬프트 재사용 |

특히 변수 템플릿은 프롬프트 관리 도구에 잘 어울립니다. 예를 들어 `{{제품명}}에 대한 {{대상 고객}}용 소개 글을 작성하세요.`를 저장해 두고, 실행할 때 변수 값만 입력하도록 만들 수 있습니다.

### 4-3. 장기 확장: 데이터베이스와 웹 인터페이스

JSON 파일이 커지고 동시 사용이나 복잡한 검색이 필요해지면 SQLite를 검토할 수 있습니다. SQLite는 별도 서버 없이 파일 하나로 동작하며, Python 표준 라이브러리의 `sqlite3` 모듈로 접근할 수 있습니다.

| 확장 방향 | 적합한 상황 | 핵심 기술 |
| --- | --- | --- |
| SQLite 전환 | 데이터가 많고 검색·정렬 조건이 다양함 | `sqlite3`, 테이블, 인덱스, FTS |
| 웹 화면 | 브라우저에서 편하게 검색·수정하고 싶음 | Flask 또는 FastAPI, HTML/CSS |
| 사용자 로그인 | 여러 사람이 각자 프롬프트를 관리함 | 인증, 사용자별 데이터 분리 |
| 공유와 권한 | 팀 프롬프트 라이브러리가 필요함 | 읽기·편집 권한, 변경 이력 |
| 백업·동기화 | 여러 PC에서 같은 데이터를 사용함 | 파일 백업, 클라우드 저장소, 충돌 정책 |

웹 화면과 외부 AI API를 연결하는 기능은 가장 마지막에 추가하는 것이 좋습니다. API 키는 코드나 GitHub에 넣지 말고 환경 변수나 비밀 관리 기능으로 보관해야 하며, 실제 업무 프롬프트를 외부 서비스로 전송할 때는 개인정보와 기밀 정보가 포함되지 않았는지도 확인해야 합니다.

## 5. 코드 품질과 테스트 개선 아이디어

기능이 늘수록 테스트도 함께 늘려야 합니다. 현재 테스트는 기본 데이터, 번호 검증, 카테고리, 검색을 확인합니다. 다음 단계에서는 입력 흐름과 파일 저장 오류까지 검증 범위를 넓힐 수 있습니다.

| 개선 항목 | 구체적인 방법 | 기대 효과 |
| --- | --- | --- |
| 입력 흐름 테스트 | `unittest.mock.patch`로 `input()`을 대체 | 빈 입력·잘못된 번호·메뉴 복귀를 자동 검증 |
| 출력 테스트 | `io.StringIO`로 `print()` 결과 캡처 | 목록·상세 화면의 문구를 안정적으로 확인 |
| 저장 테스트 | 임시 폴더와 임시 JSON 파일 사용 | 실제 데이터 파일을 건드리지 않고 저장·복구 확인 |
| 정적 검사 | formatter·linter·type checker 도입 | 들여쓰기, 사용하지 않는 코드, 타입 오류 조기 발견 |
| 모듈 분리 | `models.py`, `storage.py`, `services.py`, `cli.py`로 분리 | 기능 증가 시 파일별 역할이 명확해짐 |

## 6. 추천 구현 순서

가장 실용적인 순서는 아래와 같습니다. 각 단계가 끝날 때마다 기능 단위 커밋을 만들고, 테스트를 통과한 뒤 다음 단계로 넘어가면 Git 이력과 코드 품질을 함께 관리할 수 있습니다.

1. **수정·삭제 기능**과 삭제 전 확인 메시지를 추가합니다.
2. **JSON 저장·불러오기**와 `prompts.json` Git 제외 설정을 추가합니다.
3. 프롬프트에 **고유 ID, 생성일, 수정일**을 추가합니다.
4. **태그, 정렬, 페이지 목록, 변수 템플릿**으로 탐색과 재사용 경험을 개선합니다.
5. 데이터가 충분히 많아졌을 때 **SQLite와 전문 검색**을 검토합니다.
6. 실제로 여러 사용자가 필요해졌을 때만 **웹 인터페이스, 로그인, 공유 기능**으로 확장합니다.

이 순서는 현재 과제의 단순한 구조를 유지하면서도, 실제 서비스로 성장할 때 필요한 기반을 차례로 마련하는 방식입니다.
