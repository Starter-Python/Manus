# 과제 수행 과정: 여러 API를 연결한 국내 여행 추천 프로그램

이 문서는 `travel_planner.py`가 어떤 문제를 어떻게 해결하는지 설명합니다. 과제의 목표는 한 번의 AI 호출 결과를 끝내는 것이 아니라, **LLM의 구조화된 결과를 지도 API의 입력으로 전달하고 그 결과를 다시 LLM 리포트로 통합하는 데이터 파이프라인**을 직접 만드는 것입니다.

## 1. 문제를 작업 단위로 나누기

입력은 여행 날짜 하나이지만, 최종 산출물에는 추천 지역, 날씨 요약, 행사 후보, 맛집, 1일 일정이 필요합니다. 이를 한 번의 자유 형식 답변에 맡기면 다음 단계에서 도시 이름만 안정적으로 꺼내기 어렵습니다. 따라서 프로그램은 서로 책임이 다른 세 단계로 나누어 구성했습니다.

| 단계 | 입력 | 처리 | 출력 | 다음 단계로 전달되는 핵심 값 |
|---|---|---|---|---|
| 1차 추천 | `-date` 값 | LLM 호출 + JSON 파싱·검증 | 추천 지역, 날씨, 행사 후보, 이유 | `recommended_city` |
| 맛집 검색 | `recommended_city` | Kakao Local 키워드 검색 | 표준화한 맛집 목록 | `restaurants` |
| 최종 리포트 | 1차 추천 JSON + 맛집 목록 + 오류 목록 | LLM 호출 | Markdown 여행 리포트 | 파일 저장 |

이렇게 나누면 각 단계의 입력과 출력이 명확해집니다. 특히 1차 LLM 응답을 JSON으로 제한하면 `recommended_city`를 사람이 읽어서 복사하지 않아도 다음 API의 검색어로 사용할 수 있습니다.

## 2. CLI 입력을 먼저 검증하기

`argparse`로 `-date`와 `--date`를 같은 필수 옵션으로 정의했습니다. 이후 `datetime.strptime(..., "%Y-%m-%d")`로 실제 날짜인지 검사합니다. 형식만 맞아도 존재하지 않는 날짜인 `2026-02-30`은 통과시키지 않으므로, 불필요한 API 호출 전에 사용자 입력 오류를 발견할 수 있습니다.

```bash
python travel_planner.py --date "2026-10-03"
```

잘못된 날짜를 넣으면 프로그램은 API를 호출하지 않고 `argparse`의 사용법과 오류 메시지를 출력한 뒤 종료합니다. 이는 API 비용을 낭비하지 않고 문제의 원인을 입력값으로 좁히는 가장 앞선 방어선입니다.

## 3. API 키를 코드 밖으로 분리하기

프로그램은 실행 파일과 같은 폴더에 있는 `.env`를 `load_dotenv()`로 읽습니다. 코드에는 키 값이 없고, `OPENAI_API_KEY`와 `KAKAO_REST_API_KEY`라는 **환경변수 이름만** 존재합니다. `.env`는 `.gitignore`에 등록되어 있어 GitHub에 올라가지 않습니다.

| 항목 | 관리 위치 | 코드에서 읽는 방식 | 저장소에 커밋되는가 |
|---|---|---|---|
| OpenAI 키 | `.env` 또는 셸 환경변수 | `os.getenv("OPENAI_API_KEY")` | 아니오 |
| Kakao REST API 키 | `.env` 또는 셸 환경변수 | `os.getenv("KAKAO_REST_API_KEY")` | 아니오 |
| 키 이름 예시 | `.env.example` | 사람이 `.env` 작성 시 참고 | 예, 값은 없음 |

이 분리는 보안과 운영을 모두 위한 설계입니다. 비밀 키를 소스 파일에 쓰면 Git의 모든 과거 커밋에 복제될 수 있습니다. 반대로 환경변수 방식은 키를 교체해도 프로그램 파일을 수정하거나 재커밋할 필요가 없습니다.

## 4. 1차 LLM 출력을 JSON으로 만들기

첫 LLM 호출은 여행 날짜를 받습니다. 프롬프트는 실시간 예보나 확정 행사라고 단정하지 않고, 해당 시기의 일반적인 날씨 및 행사 **후보**를 생성하도록 지시합니다. 또한 Chat Completions의 `response_format`에 JSON Schema를 전달하여 출력 모양을 제한합니다. OpenAI의 Chat Completions API는 구조화된 응답 형식을 제공하며, 프로그램은 그 결과를 `json.loads()`로 파싱합니다.[1]

```json
{
  "recommended_city": "강릉",
  "weather": "가을 초입에는 일교차가 있으므로 얇은 겉옷이 필요합니다.",
  "events": ["지역 가을 문화행사 후보", "해변 산책 프로그램 후보"],
  "reason": "선선한 날씨에 해변과 도심을 함께 즐기기 좋습니다. ..."
}
```

파싱만 성공했다고 충분하지는 않습니다. `validate_recommendation()`은 다음을 한 번 더 확인합니다.

| 검사 대상 | 검사 이유 |
|---|---|
| 네 개의 필수 키 존재 | 다음 단계에 필요한 데이터 누락 방지 |
| `recommended_city`, `weather`, `reason`이 문자열 | 검색어와 리포트 문장으로 안전하게 사용 |
| `events`가 배열이고 각 항목이 문자열 | 반복 출력 시 형식 오류 방지 |
| 주요 문자열이 비어 있지 않음 | 빈 검색어로 장소 API를 호출하는 문제 방지 |

LLM은 일반 텍스트 생성기이므로 드물게 JSON이 깨지거나 키가 누락될 수 있습니다. 이 프로그램은 첫 실패 시에만 “필수 키 네 개를 포함한 JSON 객체만 다시 반환하라”는 보정 프롬프트로 **한 번 재시도**합니다. 두 번째도 실패하면 무한 반복하지 않고 오류를 안내하며 종료합니다.

## 5. 추천 도시를 Kakao Local API의 검색어로 연결하기

1차 JSON이 검증되면 `recommended_city`를 꺼내 `"{도시} 맛집"` 검색어를 만듭니다. 이 값이 LLM 단계와 장소 검색 단계를 연결하는 핵심 인터페이스입니다.

```python
query = f"{city} 맛집"
requests.get(
    KAKAO_KEYWORD_URL,
    headers={"Authorization": f"KakaoAK {kakao_key}"},
    params={"query": query, "size": 5},
    timeout=20,
)
```

Kakao Local 키워드 장소 검색은 GET 방식으로 요청하며, 인증에는 `Authorization: KakaoAK {REST_API_KEY}` 헤더를 사용합니다.[2] 응답의 Kakao 고유 필드명은 `normalize_place()`에서 과제 공통 형식으로 바꿉니다.

| Kakao 응답 필드 | 저장하는 공통 필드 | 이유 |
|---|---|---|
| `place_name` | `name` | 리포트에 표시할 장소명 |
| `road_address_name` 또는 `address_name` | `address` | 도로명 우선 주소 |
| `category_name` | `category` | 장소 분류 정보 |
| `place_url` | `url` | 상세 페이지 링크 |
| `x`, `y` | `x`, `y` | 경도·위도 좌표 |

`size=5`를 지정하여 권장 개수인 최대 5곳을 가져옵니다. 장소가 0건이거나 지도 API가 실패하면 빈 목록 `[]`을 반환하되, 프로그램은 멈추지 않습니다. 이는 외부 서비스의 일시 오류가 전체 사용자 경험을 망치지 않게 하는 **점진적 성능 저하(graceful degradation)** 전략입니다.

## 6. 최종 LLM 리포트를 생성하기

두 번째 LLM 호출의 입력은 다음 세 데이터 묶음입니다.

```json
{
  "recommendation": {"...": "1차 추천 JSON"},
  "restaurants": ["...맛집 목록 또는 빈 배열..."],
  "errors": ["...발생한 오류 목록..."]
}
```

모델에는 이 입력 데이터만 근거로 Markdown을 작성하라고 명시했습니다. 리포트에는 추천 지역, 추천 이유, 날씨, 행사/축제, 맛집, 1일 일정, 오류 요약의 제목을 모두 포함하도록 지시합니다. 맛집 목록이 비어 있으면 **데이터 없음**을 쓰도록 했으므로 장소 API 문제를 숨기거나 임의의 맛집을 지어내지 않습니다.

최종 LLM 호출 자체가 실패하는 경우에는 이미 확보한 1차 추천 데이터와 맛집 목록으로 `fallback_report()`가 최소 Markdown 리포트를 만듭니다. 따라서 `results/`에는 최대한 사용 가능한 결과가 남습니다.

## 7. 오류를 데이터로 관리하고 파일로 남기기

모든 외부 호출은 `try-except`로 감쌉니다. 오류는 콘솔에만 출력하지 않고 `errors` 목록에 `{step, type, message}` 구조로 축적합니다. 오류 메시지에 우연히 키가 들어간 경우를 대비해 `redact_secrets()`가 환경변수 값과 일반적인 키 패턴을 `[REDACTED]`로 바꿉니다.

| 오류 종류 | 예시 | 처리 정책 |
|---|---|---|
| 인증 | Kakao HTTP 401/403 | 맛집 빈 목록, `AUTH_ERROR` 기록, 리포트 계속 |
| 쿼터 | Kakao HTTP 429 | 맛집 빈 목록, `QUOTA_ERROR` 기록, 리포트 계속 |
| 네트워크 | 타임아웃·연결 실패 | 맛집 빈 목록, 오류 기록, 리포트 계속 |
| 응답 파싱 | JSON이 아니거나 필드 형식 오류 | 추천 JSON은 1회 재시도, 장소는 빈 목록으로 계속 |
| LLM 키 미설정 | `OPENAI_API_KEY` 없음 | 설정 방법을 알리고 즉시 종료 |

지도 키가 없는 경우도 장소 검색 단계의 구성 오류로 기록하고 빈 목록으로 처리합니다. LLM 키는 여행의 핵심 추천·리포트 두 단계를 모두 수행할 수 없으므로 즉시 종료합니다. 이 구분으로 최소 결과를 만들 수 있는 경우에는 계속 진행하면서도, 핵심 기능을 수행할 수 없는 경우에는 오해를 일으키는 불완전한 결과를 방지합니다.

## 8. 결과 파일 저장하기

`write_results()`는 실행 날짜를 파일명에 포함해, 여러 날짜의 실행 결과가 서로 덮어쓰이지 않게 합니다.

```text
results/
├── 2026-10-03_travel_data.json
└── 2026-10-03_travel_plan.md
```

원본 JSON은 1차 추천 데이터, 표준화된 맛집 배열, 오류 배열을 포함합니다. Markdown 리포트는 사람이 읽는 최종 결과입니다. 두 파일을 함께 저장하면 “왜 이 리포트가 만들어졌는지”를 추적할 수 있고, 오류가 났을 때 어떤 API 단계가 실패했는지도 확인할 수 있습니다.

## 9. REST와 HTTP 메서드를 이 과제에 연결해 이해하기

> **REST API**는 URL로 자원을 식별하고 HTTP 요청·응답으로 데이터를 주고받는 방식의 설계 원칙입니다. 이 과제에서는 JSON이 요청 또는 응답 데이터 형식으로 사용됩니다.

| 비교 항목 | GET | POST | 이 프로그램의 예 |
|---|---|---|---|
| 주된 목적 | 서버의 데이터를 조회 | 서버가 요청 본문을 처리하여 생성·변환 작업 수행 | 맛집 조회 / LLM 생성 |
| 입력 전달 위치 | URL의 쿼리 파라미터 | 요청 본문(body) | `query=강릉 맛집` / `messages=[...]` |
| 일반적 부작용 | 조회 중심 | 처리 결과를 새로 생성할 수 있음 | 장소 목록 수신 / 추천·리포트 텍스트 생성 |
| 프로그램 라이브러리 | `requests.get()` | OpenAI SDK의 Chat Completions 호출 | Kakao Local / OpenAI |

Kakao Local의 키워드 검색은 검색 조건을 전달해 장소 데이터를 조회하는 GET API입니다.[2] OpenAI Chat Completions는 사용자 메시지와 모델 옵션이 담긴 본문을 보내 새로운 출력물을 생성하는 POST API입니다.[1] 두 API의 역할 차이 때문에 데이터는 같은 JSON이라도 요청 방식과 오류 대응 방식이 다릅니다.
